# V2.1 — прототип просмотра пройденного пути (browse)

Статус: реализовано в ветке `feat/V21-browse-proto` (2026-10-08) поверх P07/P08 (непрерывный мир, `ChaseAnimation`, `WalkCycle`). Основание — задание владельца `docs/design/KIMI_AROUND_THE_WORLD_V2_PROMPT.md` (в основном worktree `mobile`), §3.1 «Динамическая сцена с просмотром пройденного». Это прототип на debug-данных: прод-экран `JourneyHome.kt` не подключён (отдельная задача V2.3 после художественной приёмки P08).

## Трактовка требований §3.1 (зафиксирована для спецификации)

- **Две позиции.** `progressPosition` — подтверждённая позиция из данных экспедиции (шаги, события, штампы, транспорт текущего прогресса). `browsePosition` — чисто визуальная позиция камеры при просмотре. Просмотр НИКОГДА не изменяет шаги, расстояние, события и штампы: вся browse-математика только читает подтверждённую позицию.
- **Граница — только будущее.** Отмотать можно назад по уже пройденному пути; вперёд за подтверждённую позицию нельзя — ни жестом, ни инерцией (жёсткий кламп, без перелёта и отскока). Из прошлого вперёд к текущей позиции вернуться можно: запрет касается будущего участка, а не направления жеста.
- **Синхронизация не вырывает.** Новая подтверждённая позиция во время просмотра только двигает границу: камера остаётся на просматриваемом месте, метка «Просмотр пройденного» сохраняется.
- **Корректировка назад ужимает.** Если подтверждённая позиция уменьшилась ниже просматриваемой, browse ужимается к новой границе (плавный догон через `ChaseAnimation`, ≤ 2 с). Ранее открытые истории/штампы корректировка не трогает (в прототипе не затрагивается — демо их не имеет; это правило прод-модели, здесь зафиксировано как контракт).
- **Метка и возврат.** При `browse < confirmed − ε` (ε = 0.01 позиции) показывается компактная метка «Просмотр пройденного» с кнопкой «К текущей позиции». Возврат — через существующий `ChaseAnimation`: точный snap к цели ≤ 2 с, затем сон покадрового цикла. Повторное нажатие — no-op (идемпотентно).
- **Reduced-motion.** Перетаскивание следует пальцу напрямую (это поведение одинаково всегда); инерции нет; «К текущей позиции» — мгновенный snap.

## Реализация

Всё в `app/src/main/java/com/boxowl/aroundtheworld/expedition/scene/SeamlessJourneyCanvas.kt` (+ unit-тесты, + debug-демо). Прод-вызовы канваса не изменили сигнатуру (`browseEnabled: Boolean = false` по умолчанию — прод-экран получает байт-в-байт прежнее поведение).

- **`JourneyBrowse`** (internal object, чистые функции): `clampBrowse` (всегда `[0, confirmed]`), `dragDeltaPositions` (px → позиции через высоту канваса и `SEGMENT_LENGTH`; контент следует за пальцем), `inertiaVelocityAt` (экспоненциальное затухание, τ = 0.18 с), `effectiveTarget` (цель рендера = `browse ?: confirmed`, никогда впереди confirmed), `squeezeBrowse` (ужатие при смене confirmed), `isBrowsing` (порог метки ε).
- **Жест** — `detectHorizontalDragGestures` на канвасе: палец — прямое следование (запись в `position` напрямую, камера строго за пальцем); отпускание — короткая инерция с жёстким клампом: движение вперёд встаёт ровно на confirmed и обрывается, назад — на 0. Новый жест отменяет летящую инерцию.
- **Владение камерой** (`JourneyBrowse.CameraOwner`, исправление по ревью PR #14): в каждый момент позицию пишет ровно один владелец — `CHASE` (план догона), `DRAG` (палец) или `INERTIA` (флинг). `onDragStart` атомарно захватывает владение из любого состояния (сначала отменяется job инерции, потом выставляется `DRAG` — отложенный `finally` отменённого флинга не может понизить `DRAG` обратно). Покадровый цикл проверяет `chaseMayWrite` ПЕРЕД применением каждого кадра: захваченный на лету план не применяет ни одного протухшего кадра — позиция не откатывается к старому плану. `onDragEnd` передаёт владение флингу (`INERTIA`) либо сразу плану; инерция держит владение до полной остановки и отдаёт его в `finally` только если всё ещё владеет. После возврата владения план репланируется от текущего отображаемого значения (без прыжка к догестовой точке). Пока владение не у плана, цикл спит на `snapshotFlow { cameraOwner }`.
- **Цикл камеры** — прежний покадровый цикл P08, но цель заменена на `effectiveTarget`; в покое цикл спит на `snapshotFlow { cameraOwner to effectiveTarget }`. Догон к confirmed после «К текущей позиции» — тот же `ChaseAnimation` (точный snap ≤ 2 с). Смена confirmed во время догона — replan с текущего кадра (как в P08).
- **WalkCycle** работает в обе стороны без изменений: фаза от ΔworldX, при отмотке назад шаг идёт вспять, в покое фаза заморожена, на палубе (DECK) герой стоит. Gait при жесте/инерции считается от скорости перетаскивания; после остановки обнуляется тем, кто двигал камеру последним (цикл покоя gait не трогает — иначе бы он гасил шаг во время активного драга).
- `position` переведён с `Animatable` на `mutableFloatStateOf` — жест пишет позицию синхронно из колбэка драга без корутинного mutex; семантика первого кадра (старт сразу в сохранённой позиции) сохранена.
- **Метка/кнопка** — `Surface`-пилюля по центру сверху с `statusBarsPadding()` (первая версия попадала под статус-бар и перехватывалась системным окном — исправлено). Показывается только при `browseEnabled && isBrowsing`.

## Debug-демо

`JourneyDemoActivity` (только debug source set, только в памяти — Room/Health Connect не затрагиваются):

- Переключатель «Просмотр: вкл/выкл» (вторая строка кнопок — первая не помещалась).
- Extras: `--ez browse true` — browse сразу включён; `--ei confirmdelay <сек> --ef confirmdelta <позиций>` — сдвиг подтверждённой позиции через задержку (имитация синхронизации во время просмотра, в обе стороны).
- Счётчик «кадр N» внизу панели: `screenrecord` на эмуляторе кодирует только изменения экрана, а мир P07/P08 в покое намеренно не перерисовывается — без тика статичные сцены писались бы по единицам кадров. Тик гоняет композитор каждый кадр и доказывает, что неподвижная запись — это неподвижная сцена, а не ступор энкодера. Только для записей, на логику не влияет.
- Запуск: `adb shell am start -n com.boxowl.aroundtheworld/.debug.JourneyDemoActivity --ef start 6 --ez browse true`

## Ограничения (честно)

- Видео — debug-демонстрация на эмуляторе, НЕ подтверждение реальных шагов; физическая приёмка P02/Q01 не затрагивается. `screenrecord` на эмуляторе кодирует только изменения экрана, а мир в покое не перерисовывается по решению P08 — поэтому статичные сцены сняты с debug-тиком «кадр N» (см. демо), а ранние дубли с единичными кадрами выброшены. Во время первой сессии записи параллельная сессия делила эмулятор (дважды переустановила APK — те дубли (б) тоже выброшены и перезаписаны). Плавность жеста на физическом устройстве не проверялась, 60 fps не заявляем.
- Скорость инерции оценивается по межсобытийным dt (скольжение 50/50), а не по `VelocityTracker`; при очень рваных событиях возможна неточность начальной скорости флинга — кламп границы от этого не зависит.
- Метка/кнопка — минимальная пилюля Material3 для прототипа; финальное расположение и вид — задача прод-подключения.
- `contentDescription` сцены по-прежнему описывает подтверждённую позицию, а не просматриваемую — осознанное упрощение прототипа; для прода стоит озвучивать режим просмотра.
- Просмотр будущего на глобусе (вкладка «Карта», §5) — отдельная сущность, этим прототипом не ограничивается.

## Что нужно для прод-подключения (V2.3, JourneyHome)

1. Передать `browseEnabled = true` в вызов `SeamlessJourneyCanvas` из `JourneyHome.kt` (однострочное изменение; сигнатура уже поддерживает).
2. Согласовать размещение пилюли «Просмотр пройденного / К текущей позиции» с оболочкой JourneyHome (индикаторы дня/шагов, пилюля события) и финальные тексты/стиль.
3. Accessibility: озвучивать вход/выход из режима просмотра и просматриваемую позицию.
4. Проверить на физическом устройстве вместе с P02/Q01: жест не конфликтует с горизонтальными элементами экрана, инерция и кламп при реальных синхронизациях Health Connect, отсутствие лишних перерисовок в покое.
