# V2.2d — первый пользовательский вход в v2

Старт: 2026-11-12. Ветка `feature/v22d-v2-state`, worktree `/private/tmp/mobile-v22d-v2-state`, база `9c335f5` после PR #31. Источники: `docs/design/v2-product-decisions.md`, `docs/SPEC.md`, `V2CreditRepository.kt`, `V2StepSync.kt`.

## Результат

Пользователь может явно создать v2-экспедицию с выбором режима и длины шага в сантиметрах, видеть сохранённый v2-прогресс и паспорт после перезапуска, вручную запустить сверку шагов и начать новую попытку с подтверждением. v1-данные остаются в Room и не конвертируются. При активной v2 первым открывается её экран. Полный художественный глобус, история попыток и аппаратная приёмка вынесены из этого блока.

## Границы

Разрешены новые `expedition/V2ExpeditionViewModel.kt` и `expedition/V2JourneyScreen.kt`, точечная маршрутизация в `ExpeditionPanel.kt`, соответствующие unit/androidTest, этот документ и `TODO.md`. Не менять Room-схему/DAO, арифметику `CreditLedger`, `V2StepSync`, Health Connect permissions/gateway, v1-модель/сверку, пороги, ассеты и Gradle. Если UI требует новых данных за пределами снимка v2, сначала зафиксировать контракт, а не дублировать расчёт в Compose.

## Критерии

1. Старт v2 всегда явный и подтверждённый. Длина шага по умолчанию 75 см, пользователь может заменить её до старта; значение хранится в миллиметрах и далее не меняется. Показать, что это игровая оценка, что v1 скрывается из первого v2 UI и что 80-дневное пари трудно достижимо при текущем балансе.
2. Существующая активная v2 загружается прежде v1 UI; повторный старт с `expectedActiveSeq` атомарно архивирует прежнюю попытку без потери шагов/штампов. Ошибка/отказ доступа не превращаются в ноль. v1 продолжает работать без v2.
3. Экран v2 показывает расчётные реальные и книжные километры раздельно, состояние синхронизации, паспорт с `NULL` как «дата неизвестна», и не выводит выдуманный дневной итог. Навигация первого v2: «Путь · Карта · Паспорт · Настройки»; карта может использовать уже готовые read-only карточки остановок, художественный production-глобус — следующий блок.
4. Проверить создание, перезапуск, новую попытку, отказ доступа, сохранность v1 и UI на эмуляторе. Сборка, unit, lint, instrumentation и CI зелёные. Отдельное строгое ревью межмодульной интеграции до слияния; P02/F02/Q01 остаются на физическом телефоне.

Порядок: карта контрактов текущих ViewModel/UI → реализация состояния и явного входа → экран и тесты → строгое ревью → эмулятор/CI → PR и автоматическое слияние → передача следующей задачи.
