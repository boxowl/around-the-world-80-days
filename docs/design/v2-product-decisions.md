# Продуктовые решения для первого рабочего v2

Дата: 2026-11-10. Решения приняты Codex по прямому поручению владельца самостоятельно закрыть открытые вопросы. Это правила для **новых** v2-экспедиций; начатые v1 не пересчитываются. Аппаратная приёмка P02/F02/Q01 остаётся обязательной.

## Учёт расстояния

- Основной вход — `StepsRecord.COUNT_TOTAL` через Health Connect Aggregate без фильтра источника. `DistanceRecord` не требуется для первого v2 и не включается как запасной источник: его отсутствие не должно останавливать путешествие. Потребитель видит **расчётные реальные километры**, а не показания измерителя расстояния. В UI и документации это слово сохранять. Health Connect предоставляет отдельные агрегаты [Steps](https://developer.android.com/health-and-fitness/health-connect/features/steps) и [Distance](https://developer.android.com/health-and-fitness/health-connect/aggregate-data); наличие второго в API не гарантирует записей конкретного браслета.
- На старте v2 показывать длину шага в сантиметрах: значение по умолчанию **75 см** — игровое предположение, а не измерение пользователя; его можно заменить до подтверждения старта. Сохранить выбранную длину в миллиметрах в `expedition_v2`. После старта она неизменна; новый выбор действует только в новой экспедиции. Молчаливого пересчёта пройденных дней нет.
- Один дневной подтверждённый агрегат шагов переводить в целые расчётные метры как `floor(steps × strideMillimeters / 1000)` с проверкой переполнения. Затем обычный `CreditLedger` применяет `k=20` **один раз**. В `daily_credit` хранить исходный подтверждённый `steps` и получившиеся `realMeters` для аудита и восстановления; книжные метры/итог не дублировать. При поздней корректировке заменять оба значения дня атомарно. Отсутствие данных/ошибка/отзыв разрешения не равны нулю.
- Никакой автоматической смеси Steps и Distance и никакого суммирования источников вручную. Фактические приоритеты телефон+браслет и поступление шагов — предмет физического теста. Если на устройстве шаги не поступают, это блокер приёмки устройства, а не основание подменять неизвестное значение нулём.
- Окно повторного сканирования 119 дней оставляем как известное ограничение первого v2; корректировки старше окна автоматически не обнаруживаются. Удалять уже сохранённые дни при недоступности старого Health Connect интервала нельзя. Расширение окна и `READ_HEALTH_DATA_HISTORY` — отдельная задача после наблюдений на устройстве.

## Экспедиция и пари

- C-lite и паспорт C1 подтверждены владельцем: в данных сохраняются все попытки с `expeditionSeq`, активна не более одной v2, в первом релизе нет экрана истории. Новая v2-экспедиция начинается только явным действием пользователя с подтверждением; это доступно до финиша, после истечения 80 дней без финиша и после финиша. При старте прежняя активная становится завершённой, её шаги/штампы/baseline остаются; новая начинает с нуля и получает собственную стартовую отметку Лондона. Истечение 80 дней само по себе не завершает и не стирает путь. После финиша можно показать предложение нового старта, но не запускать его автоматически.
- Существующую v1-экспедицию сохранять по старым правилам; при явном старте v2 она не конвертируется и не удаляется. Первый v2 UI показывает активную v2. Переключение назад на v1 и экран истории — будущие отдельные задачи, это должно быть прямо сказано перед подтверждением нового v2-старта.
- В v2 оставляем выбор **«Пари на 80 дней» / «Свободное путешествие»**. Для пари дедлайн и поздние корректировки следуют календарным правилам `docs/SPEC.md`; победа — достижение D = 40 502 книжных км внутри окна, просрочка не удаляет прогресс. Цель не подменять прежней шаговой нормой v1. Ожидаемая сложность 80-дневного пари при k=20 должна быть честно показана перед стартом, без обещания достижимости.

## Визуальные правила

- Цикл освещения 30 км привязан к **расчётным реальным километрам**, соответствующим текущей отображаемой позиции. В периоде 20 км светлой и 10 км тёмной части; переходы плавные, без скачка на границе 30→0. При просмотре прошлого освещение считается по просматриваемой позиции, а системное время его не меняет. Это отдельная задача рендера, не правило начисления.
- Пять спорных якорей класса C из `v23-c-d-decisions-memo.md`: пролог дом–клуб–вокзал — сцена без числового порога; «Невада» → существующий `reno`; «Юта» → `ogden`; «Ски-Камберленд» → `fort-kearney` при сохранении названия сцены; «Джерси» → `new-york` как визуальная деталь. Ни один выбор не создаёт нового узла, расстояния или второго источника порогов. Порог якоря берётся из `RouteMeasure`.
- Класс D: пакетбот и торговая Henrietta имеют различимые силуэты; Tankadere рисуется как шхуна с парусами без трубы в существующей категории, с честной подписью «шхуна Tankadere». Новую одиннадцатую категорию транспорта не добавлять без отдельной причины.

## Даты паспорта

- В Room хранить `grantedAt` как nullable ISO-8601 UTC TEXT; `NULL` в UI означает «дата неизвестна». Не вычислять историческую дату из `lastReadAt` или дня шагов. При позднем подключении паспорта прежние пороги получают `NULL`, будущие пересечения — время успешной сверки. Day-precision backfill не делать в первом v2.

## Граница реализации

Решения снимают продуктовые неопределённости для постановки V2.2b+V2.4b. Следующий шаг — отдельная feature-ветка/worktree, точные границы файлов и критерии, строгий review миграции/арифметики и проверка обновления v1→v4. Эта записка сама по себе **не подтверждает**, что конкретный телефон или браслет предоставляет шаги, и не закрывает P02/F02/Q01.
