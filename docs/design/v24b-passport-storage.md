# V2.4b — контракт хранения и восстановления штампов паспорта (предложение)

Дата: 2026-10-11. Read-only контракт по аудиту terra-research. Без кода и миграций до полной постановки и согласованных зависимостей. Основание: `docs/design/v24a-passport-task.md`, PR #18 (V2.4a, OPEN), `docs/design/v22b-proposal.md`, `ExpeditionDatabase.kt` (Room schema v3). Физические данные и источник метров проверенными не считаются.

## 1. Хранение: рекомендуемый вариант

**Новая таблица `passport_stamps(stampId TEXT PK, grantedAt TEXT NULL)`** — аддитивная миграция (один `CREATE TABLE`), прецедент формата дат — TEXT ISO-8601 nullable (как `lastReadAt`); epoch ms равнозначен при желании штаба. Семантика записи — только `INSERT IGNORE` (прецедент `unlocked_diary`), операции DELETE/UPDATE нет в принципе: повторная выдача не перезаписывает дату, откат не отзывает штамп. NULL даты — первоклассное значение «неизвестна», прямо отражает `PassportSnapshot.granted: Map<StampId, Instant?>`. Неизвестные при чтении id (из будущих версий) — пропускать, не удалять.

**Отклонено (б) — строки штампов в `unlocked_diary`:** загрузка v1 читает все stopId в `Expedition.unlocked` (`ExpeditionDatabase.kt:130`), а `Expedition.init` требует `unlocked ⊆ FIRST_LEG` (`Expedition.kt:29`) — строка `stamp-suez-finish` крашит загрузку старой экспедиции. Смешивание сущностей ломает инварианты обеих.

**Отклонено (в) — колонки/блоб в `expedition`:** теряется поштучная атомарность IGNORE, JSON-в-SQL, и меняется сущность, которую читает v1-путь.

## 2. Восстановление vs выдумывание дат (ключевое разделение)

### 2.1. Детерминированный контракт первого восстановления (базовая линия)

Проблема: наивный цикл «строки → снимок → reconcile(existing, total, observedAt=now)» на пустой таблице проставит `now` ВСЕМ уже пройденным штампам. Поэтому:

- Хранится долговечная **базовая линия** `passportBaselineBookMeters: Long` (метаданные; предложение — однострочная таблица `passport_meta` или колонка в v2-строке экспедиции; точное место — постановка).
- Правило: `observedAt` присваивается ТОЛЬКО пересечениям порогов **строго выше предыдущей сохранённой базовой линии**. Пороги ≤ базовой линии получают NULL. После каждого успешного reconcile базовая линия атомарно обновляется до текущего `totalBookMeters` в одной транзакции с дозаписью новых строк.
- Первый запуск после миграции (таблица и базовая линия пусты, у пользователя прогресс > 0): baseline трактуется как «весь текущий прогресс исторический» → все выданные штампы получают NULL, базовая линия атомарно фиксируется на текущем итоге. `observedAt=now` в этом reconcile не применяется ни к одному порогу.
- Это устраняет противоречие детерминированно: исторический прогресс отличён от нового пересечения сохранённым прошлым итогом, без эвристик.

### 2.2. Ограничение контракта (факт 2026-10-11)

`CreditLedger` в main — **чистая модель без сохранения** (`expedition/credit/CreditLedger.kt`, `DayCredit.kt`; нет Room/Store/DAO); v2-контур к Room НЕ подключён. Поэтому V2.4b НЕ обещает: автоматическую выдачу штампов при сверке и восстановление после перезапуска как работающий пользовательский сценарий — до явной точки интеграции и **долговечного источника `totalBookMeters`** (репозиторий v2). Место этой точки (репозиторий v2 vs ViewModel) фиксируется штабом в постановке V2.4b и согласуется с постановкой V2.2b, чтобы не дублировать решение о месте агрегата v2. В критериях V2.4b проверяется хранение/восстановление/базовая линия на явных вызовах хранилища, а не «само работает после сверки».

### 2.3. Восстановление (честное)

1. Загрузка: все строки `passport_stamps` → `PassportSnapshot` (неизвестные id — пропуск, не удаление) + прочитанная базовая линия.
2. Снимок — вход `PassportV1.reconcile(existing, totalBookMeters, observedAt)`; observedAt применяется по правилу базовой линии (2.1). Union гарантирует: перезапуск, откат и повторная сверка не уменьшают набор.
3. Результат дозаписывается только новыми строками (INSERT IGNORE); существующие строки и их даты (включая NULL) не перезаписываются; базовая линия обновляется атомарно с дозаписью.
4. Reconcile вызывается только для v2-экспедиции; v1 штампов не получает.

### 2.4. Даты

- Новое пересечение (порог выше базовой линии): `observedAt = now` момента сверки (существующий в пути данных, `ExpeditionSync`/`ExpeditionViewModel`) — семантика «момент, когда приложение наблюдало пересечение». Скачок через несколько глав в одной сверке — одинаковый observedAt для порогов выше базовой линии (честно).
- **Недопустимо:** вывод даты задним числом из текущего итога; `lastReadAt` как дата выдачи (это момент предыдущей сверки); подстановка `now` вместо неизвестной даты; `observedAt` порогам ≤ базовой линии. Штампы, чьи пороги пройдены до появления хранения (V2.2b вышел раньше V2.4b), сохраняются с **NULL — «дата неизвестна»** — это честное состояние, а не дефект.
- Дневная история (`daily_steps`/`daily_credit`) как источник дат **не используется**: окно пересканирования 119 дней даёт ложно поздние дни, а поздние замены делают «день пересечения» нестабильным при неоткатываемых штампах. Day-precision backfill из полной истории — отдельный вопрос владельцу, не часть контракта.

## 3. Обратная совместимость и старые экспедиции

- Экспедиция v1 не получает штампов; таблица для v1-пользователя пустая. Молчаливой конверсии v1→v2 нет.
- Миграция только аддитивная; цепочка v1→v2→v3→v4 обязана пройти на реальных старых схемах; три старые таблицы не трогаются. Деструктивного fallback в проекте нет — миграция обязательна.
- Проверки по прецедентам: instrumentation-тест миграции с ручным созданием старой схемы через `SQLiteDatabase` (прецедент `ExpeditionSchemaV2Test`) с контролем содержимого старых таблиц; ручная установка APK поверх предыдущей сборки (прецедент P08).
- Legacy `ExpeditionStore` (AtomicFile) не меняется.

## 4. Координация с V2.2b

- Жёсткая предпосылка V2.4b — **слияние PR #18** (модель только в ветке). От неутверждённого источника метров V2.2b V2.4b не зависит (нужен только слитый `CreditLedger.totalBookMeters`).
- Миграции Room линейны по версиям: **задача, которая сливается первой, занимает v3→v4; вторая делает v4→v5**. Постановки обеих задач запрещают параллельное определение одной версии. Это правило закрепить в TODO.
- Порядок допустим любой: V2.4b первой — проверяется на синтетических вызовах reconcile; V2.2b первой — штампы за уже пройденные пороги получают NULL-даты (честный контракт, не регрессия).

## 5. Критерии готовности V2.4b (предложение)

1. Сохранение/восстановление набора: выданные штампы переживают перезапуск хранилища; восстановленный снимок равен сохранённому (включая NULL-даты).
2. **Первое восстановление (обязательный сценарий штаба):** существующий v2-пользователь с прогрессом > 0 и пустой таблицей/базовой линией после миграции — все уже пройденные штампы получают **NULL**, базовая линия атомарно фиксируется на текущем итоге; следующее новое пересечение (порог выше базовой линии) получает `observedAt`, а ранее записанные NULL не перезаписываются.
3. Монотонность: запись только INSERT IGNORE; повтор не перезаписывает дату; откат прогресса не удаляет строки и не отзывает штампы (DELETE нет).
4. Откат не отзывает: корректировка CreditLedger вниз не меняет таблицу; базовая линия при откате не двигается назад (новые пересечения сравниваются с максимумом уже наблюдавшегося итога — правило фиксируется в постановке).
5. NULL не выдумывается: ни один путь кода не подставляет now/lastReadAt/дату дня вместо неизвестной; последующий reconcile с не-null observedAt не перезаписывает существующие даты.
6. Обновление поверх v1 без потери данных (миграция v1→…→v4 + ручная установка поверх); v1-экспедиция загружается, штампов не получает.
7. Существующие тесты v1 зелёные без изменения ожиданий.
8. Обязательный astra-review миграции, базовой линии и контракта восстановления; сборка/unit/lint/instrumentation зелёные; PR без автоматического слияния.
9. **Не критерии V2.4b:** работающая автоматическая выдача при сверке и восстановление как пользовательский сценарий — до явной точки интеграции и долговечного источника `totalBookMeters` (см. 2.2).
