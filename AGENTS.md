# Инструкции для coding-агентов

## Назначение проекта

«Вокруг света за 80 дней» — Android-приложение на Kotlin/Jetpack Compose. Реальные шаги из Health Connect двигают пользователя по игровому кругосветному маршруту, открывают остановки и записи дневника. Данные хранятся локально в Room; аккаунт, сервер и постоянный GPS для первой версии не нужны.

## Источники истины

- `TODO.md` — статус, зависимости, критерии готовности и ближайший шаг.
- `docs/SPEC.md` — правила календаря, часового пояса, корректировок и целей экспедиции.
- `docs/ROUTE.md` — маршрут, пороги и содержание остановок.
- `docs/F02_VERIFICATION.md`–`docs/F06_VERIFICATION.md` — проверенная реализация и ограничения.
- `docs/HEALTH_CONNECT_TEST.md` — протокол проверки на физическом телефоне.

При противоречии не меняйте продуктовые правила самостоятельно: зафиксируйте вопрос для штаба проекта.

## Правила работы

- Этот проект управляется через штаб: решения по продукту, архитектуре, приоритетам и приёмке фиксируются в `TODO.md`.
- Одна самостоятельная фича — отдельная ветка/worktree и PR. Одновременно не держать больше двух активных задач реализации.
- Перед фичей фиксировать цель, разрешённые файлы, что не трогать, зависимости, критерии готовности, ветку и план исследования/реализации/ревью.
- Миграции, расчёты, Health Connect, синхронизация, безопасность и межмодульная интеграция требуют отдельного строгого ревью.
- Не считать физическое устройство проверенным по результатам эмулятора или синтетических данных.
- Не менять пороги, календарные правила, семантику корректировок и сохранения открытий без согласования.
- Не коммитить ключи подписи, токены, `local.properties`, локальные SDK-настройки и debug APK.

## Организация в Kimi Code

- Главная Kimi-сессия workspace `mobile` — штаб: продуктовые решения, архитектура, приоритеты, интеграция и приёмка. Не превращать её в журнал реализации.
- Для отдельной фичи с собственным результатом, границами файлов и критерием готовности создавать отдельную верхнеуровневую Kimi-сессию в отдельном Git worktree. В первом сообщении фиксировать: цель, границы, что не трогать, зависимости, критерии готовности, ветку/worktree и план агентов.
- Внутри штабной или feature-сессии разрешено делегировать кастомным субагентам из `.kimi-code/agents/`:
  - `terra-research` — read-only исследование, диагностика и карта затронутых контрактов;
  - `sol-implementation` — основная реализация в согласованных границах;
  - `astra-review` — строгая проверка миграций, расчётов, синхронизации, безопасности и межмодульной интеграции;
  - `luna-mechanical` — небольшие механические правки без продуктовых решений.
- Одновременно запускать максимум двух субагентов. Параллельно допустимы независимые read-only исследования или ревью; два агента не должны одновременно менять одни и те же файлы.
- Практичный цикл: штаб согласует задачу → отдельная feature-сессия/worktree → `terra-research` исследует → `sol-implementation` реализует → `astra-review` проверяет сложные части → PR → штаб принимает и обновляет `TODO.md`.
- Для простой изолированной фичи достаточно `sol-implementation`; для диагностики использовать `terra-research`; для малой правки — `luna-mechanical`.
- Субагенты Kimi не видят историю штабной сессии. В каждом делегировании явно передавать цель, границы файлов, зависимости, критерии готовности и необходимые источники истины.
