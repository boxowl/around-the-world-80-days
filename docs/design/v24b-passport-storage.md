# V2.4b — контракт хранения и восстановления штампов паспорта (предложение)

Дата исходного контракта: 2026-10-11. Обновлён 2026-11-10 после выбора владельцем **C-lite и отдельного паспорта каждой экспедиции (C1)**. По его поручению остальные продуктовые решения для первого v2 зафиксированы в `v2-product-decisions.md`. Без кода и миграций до полной постановки. Основание: `docs/design/v24a-passport-task.md`, слитый PR #18 (V2.4a), `docs/design/v22b-v24b-dependency-map.md`, `ExpeditionDatabase.kt` (Room schema v3). Физические данные не проверены.

## 1. Хранение: рекомендуемый вариант

**Новая таблица `passport_stamps(expeditionSeq, stampId, grantedAt NULL)`, PK `(expeditionSeq, stampId)`** — паспорт каждой экспедиции хранится отдельно. Даты — nullable TEXT ISO-8601 UTC; `NULL` показывать как «дата неизвестна». Семантика записи — `INSERT IGNORE` **в namespace одной экспедиции**; повторная выдача не перезаписывает дату, откат не отзывает штамп. Завершённые экспедиции и их штампы не удаляются. NULL даты — первоклассное значение, прямо отражает `PassportSnapshot.granted: Map<StampId, Instant?>`. Неизвестные при чтении id (из будущих версий) — пропускать, не удалять.

**Отклонено (б) — строки штампов в `unlocked_diary`:** загрузка v1 читает все stopId в `Expedition.unlocked` (`ExpeditionDatabase.kt:130`), а `Expedition.init` требует `unlocked ⊆ FIRST_LEG` (`Expedition.kt:29`) — строка `stamp-suez-finish` крашит загрузку старой экспедиции. Смешивание сущностей ломает инварианты обеих.

**Отклонено (в) — колонки/блоб в `expedition`:** теряется поштучная атомарность IGNORE, JSON-в-SQL, и меняется сущность, которую читает v1-путь.

## 2. Восстановление vs выдумывание дат (ключевое разделение)

### 2.1. Детерминированный контракт первого восстановления (базовая линия)

Проблема: наивный цикл «строки → снимок → reconcile(existing, total, observedAt=now)» на пустой таблице проставит `now` ВСЕМ уже пройденным штампам. Поэтому:

- Базовая линия `passportBaselineBookMeters: Long` хранится **отдельно для каждой экспедиции** в `passport_meta(expeditionSeq PK, baselineBookMeters INTEGER NOT NULL DEFAULT 0)` (часть той же аддитивной миграции; не колонка v1-таблицы `expedition`).
- `PassportV1.reconcile` принимает один `observedAt` на вызов, поэтому применяется **двухпроходный алгоритм в одной транзакции**:
  1. Исторический проход: `snapshot1 = reconcile(existing, min(total, baseline), observedAt = null)` — все пороги ≤ базовой линии получают NULL.
  2. Проход новых пересечений: `snapshot2 = reconcile(snapshot1, total, observedAt = now)` — пороги выше базовой линии получают дату. Пороги ≤ базовой линии уже есть в `snapshot1` с NULL, union их не переписывает.
  3. Дозапись новых строк `(expeditionSeq, stampId)` (INSERT IGNORE) и обновление базовой линии **того же `expeditionSeq`** — атомарно, в той же транзакции.
- **Первый запуск после миграции** (таблица и базовая линия пусты, прогресс > 0): базовая линия для этого вызова считается равной текущему `total` → выполняется только исторический проход (проход 2 пуст, все штампы получают NULL), затем базовая линия записывается.
- **Обновление базовой линии: `baseline := max(previousBaseline, total)` после каждой успешной записи, в том числе при откате прогресса** (при откате baseline = previousBaseline, т.е. не двигается назад). Это техническое следствие монотонности: базовая линия — «максимум итога, уже наблюдавшегося хранилищем»; правило утверждено, открытым вопросом не остаётся.

### 2.2. Ограничение контракта (факт 2026-10-11)

`CreditLedger` в main — **чистая модель без сохранения** (`expedition/credit/CreditLedger.kt`, `DayCredit.kt`; нет Room/Store/DAO); v2-контур к Room НЕ подключён. Поэтому V2.4b НЕ обещает: автоматическую выдачу штампов при сверке и восстановление после перезапуска как работающий пользовательский сценарий — до явной точки интеграции и **долговечного источника `totalBookMeters`** (репозиторий v2). Место этой точки (репозиторий v2 vs ViewModel) фиксируется штабом в постановке V2.4b и согласуется с постановкой V2.2b, чтобы не дублировать решение о месте агрегата v2. В критериях V2.4b проверяется хранение/восстановление/базовая линия на явных вызовах хранилища, а не «само работает после сверки».

### 2.3. Восстановление (честное)

1. Загрузка: только строки `passport_stamps` выбранного `expeditionSeq` → `PassportSnapshot` (неизвестные id — пропуск, не удаление) + базовая линия той же экспедиции. Смешивать штампы разных экспедиций нельзя.
2. Снимок — вход `PassportV1.reconcile(existing, totalBookMeters, observedAt)`; observedAt применяется по правилу базовой линии (2.1). Union гарантирует: перезапуск, откат и повторная сверка не уменьшают набор.
3. Результат дозаписывается только новыми строками `(expeditionSeq, stampId)` (INSERT IGNORE); существующие строки и их даты (включая NULL) не перезаписываются; базовая линия той же экспедиции обновляется атомарно с дозаписью.
4. Reconcile вызывается только для v2-экспедиции; v1 штампов не получает.

### 2.4. Даты

- Новое пересечение (порог выше базовой линии): `observedAt = now` момента сверки (существующий в пути данных, `ExpeditionSync`/`ExpeditionViewModel`) — семантика «момент, когда приложение наблюдало пересечение». Скачок через несколько глав в одной сверке — одинаковый observedAt для порогов выше базовой линии (честно).
- **Недопустимо:** вывод даты задним числом из текущего итога; `lastReadAt` как дата выдачи (это момент предыдущей сверки); подстановка `now` вместо неизвестной даты; `observedAt` порогам ≤ базовой линии. Штампы, чьи пороги пройдены до появления хранения (V2.2b вышел раньше V2.4b), сохраняются с **NULL — «дата неизвестна»** — это честное состояние, а не дефект.
- Дневная история (`daily_steps`/`daily_credit`) как источник дат **не используется**: окно пересканирования 119 дней даёт ложно поздние дни, а поздние замены делают «день пересечения» нестабильным при неоткатываемых штампах. Day-precision backfill не входит в первый v2.

## 3. Обратная совместимость и старые экспедиции

- Экспедиция v1 не получает штампов; таблица для v1-пользователя пустая. Молчаливой конверсии v1→v2 нет.
- Миграция только аддитивная; цепочка v1→v2→v3→v4 обязана пройти на реальных старых схемах; три старые таблицы не трогаются. Деструктивного fallback в проекте нет — миграция обязательна.
- Проверки по прецедентам: instrumentation-тест миграции с ручным созданием старой схемы через `SQLiteDatabase` (прецедент `ExpeditionSchemaV2Test`) с контролем содержимого старых таблиц; ручная установка APK поверх предыдущей сборки (прецедент P08).
- Legacy `ExpeditionStore` (AtomicFile) не меняется.

## 4. Координация с V2.2b

- PR #18 и чистый `CreditLedger` уже в main. Для пользовательского сценария нужен долговечный `totalBookMeters` активной v2-экспедиции; объединённая V2.2b+V2.4b — владелец общей миграции v3→v4. Источник расчётных метров выбран в `v2-product-decisions.md`.
- Все четыре новые таблицы используют C-lite namespace. Активная экспедиция выбирается по `expedition_v2.state = ACTIVE`; на первом релизе она не более одной. Новый старт оставляет паспорт прежней экспедиции на месте и создаёт пустой паспорт в новом namespace.

## 5. Критерии готовности V2.4b (предложение)

1. Сохранение/восстановление набора **для данного `expeditionSeq`**: выданные штампы переживают перезапуск хранилища; восстановленный снимок равен сохранённому (включая NULL-даты). Две экспедиции не смешиваются; новая начинает с отдельной стартовой отметки.
2. **Первое восстановление (обязательный сценарий штаба):** существующий v2-пользователь с прогрессом > 0 и пустой таблицей/базовой линией после миграции — все уже пройденные штампы получают **NULL** (только исторический проход), базовая линия атомарно фиксируется на текущем итоге; следующее новое пересечение (порог выше базовой линии) получает `observedAt`, а ранее записанные NULL не перезаписываются.
3. **Скачок через исторический и новый пороги за один вызов (двухпроходный тест):** baseline между двумя порогами глав; один reconcile-вызов с total выше обоих — исторический порог получает NULL (проход 1), новый — `observedAt` (проход 2); обе записи атомарны; повторный вызов идемпотентен.
4. Монотонность: запись только INSERT IGNORE по составному ключу; повтор не перезаписывает дату; откат прогресса не удаляет строки и не отзывает штампы (DELETE нет).
5. Откат не отзывает: корректировка CreditLedger вниз не меняет таблицу; **базовая линия при откате не двигается назад — `baseline := max(previousBaseline, total)` для этой экспедиции.**
6. NULL не выдумывается: ни один путь кода не подставляет now/lastReadAt/дату дня вместо неизвестной; последующий reconcile с не-null observedAt не перезаписывает существующие даты.
7. Обновление поверх v1 без потери данных (миграция v1→…→v4 + ручная установка поверх); v1-экспедиция загружается, штампов не получает.
8. Существующие тесты v1 зелёные без изменения ожиданий.
9. Обязательный строгий review миграции, базовой линии и контракта восстановления; сборка/unit/lint/instrumentation зелёные; PR без автоматического слияния.
10. **Не критерии V2.4b:** работающая автоматическая выдача при сверке и восстановление как пользовательский сценарий — до явной точки интеграции и долговечного источника `totalBookMeters` (см. 2.2).
