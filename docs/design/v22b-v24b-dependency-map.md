Исходная карта: 2026-10-12. ## 1. Целевая схема поверх v3 (решение по ключам)

Сейчас: `expedition` (1 строка), `daily_steps`, `unlocked_diary`, version 3, `exportSchema = false`.

| Сущность | Размещение | Аргумент |
|---|---|---|
| Дневной зачёт v2 | новая `daily_credit(expeditionSeq, date, steps, realMeters)`, PK `(expeditionSeq, date)` | подтверждённые шаги и расчётные целые метры этого дня; книжные метры не хранить (производные ×20, k применяется один раз в `CreditLedger`) |
| Параметры v2 | новая `expedition_v2(id PK, state, endedAt, strideMillimeters, …)`, где `id = expeditionSeq` | одна активная v2-строка, старые строки сохраняются; выбранная при старте длина шага неизменна. v1-таблица `expedition` не трогается; `sourceKind` не нужен в первом v2 с единственным источником |
| Штампы | новая `passport_stamps(expeditionSeq, stampId, grantedAt NULL)`, PK `(expeditionSeq, stampId)` | паспорт C1 каждой экспедиции свой; `unlocked_diary` v1 не используется |
| Базовая линия | новая `passport_meta(expeditionSeq PK, baselineBookMeters)` | базовая линия выдачи штампов отделена для каждой экспедиции |

**Сосуществование v1/v2:** `Expedition.init` крашится на `routeVersion != 1` (`Expedition.kt:23`), поэтому **v2 не пишет в таблицу `expedition` вообще**; v2-агрегат живёт в своих таблицах, v1-путь его не знает. DAO — отдельные `CreditDao`/`PassportDao`, v1-DAO не разрастается.

**Инвариант C-lite:** не более одной `expedition_v2.state = ACTIVE`; новый старт только по явному действию с подтверждением атомарно завершает прежнюю активную строку и создаёт новую с новым `expeditionSeq`, не переносит и не стирает её дневные записи, штампы или baseline. В первом релизе нет экрана истории. Истечение 80 дней до D не выполняет этот переход автоматически. Старая v1 остаётся в данных; UI после явного старта показывает v2, без переключения назад в первом релизе.

## 2. Восстановление snapshot при холодном старте (v2)

1. Найти единственный активный `expedition_v2.id`; все дальнейшие запросы ограничить этим `expeditionSeq`, не смешивая историю разных экспедиций.
2. `passport_stamps` активной экспедиции → `PassportSnapshot` (неизвестные id — пропуск, не удаление) + её `passport_meta.baselineBookMeters`.
3. Её `daily_credit` → `CreditLedger.of(map)` → `totalBookMeters`. **Долговечный итог не хранится** — всегда вычисляется из суммы строк этой экспедиции.
4. Двухпроходный reconcile по её базовой линии в одной транзакции: `reconcile(existing, min(total, baseline), null)` → `reconcile(snapshot1, total, now)` → дозапись по `(expeditionSeq, stampId)` (INSERT IGNORE) + `baseline := max(baseline, total)` атомарно; при откате baseline назад не двигается.
5. v1-экспедиция не читает и не получает ничего из новых таблиц.

## 3. Связь с контуром Health Connect

Контур `ExpeditionSync.kt:33-67` переиспользуется: окна в поясе экспедиции, первый день от `startedAt`, окно скана 119 дней, `null` = gap (день неизменён), отзыв доступа посреди скана — ничего не пишется, полный провал — `ReadError`, stale-guard `lastReadAt`. Граница истории HC — 30 дней до первой выдачи разрешения; `READ_HEALTH_DATA_HISTORY` не предлагать. Контракт шлюза (`StepTotal(count, origins)`) не меняется.

**Источник расчётных метров решён для первого v2:** Health Connect Steps Aggregate; `floor(steps × strideMillimeters / 1000)` по каждому подтверждённому дню, длина шага по умолчанию 750 мм с изменением пользователем **до** старта, далее неизменна. Неизвестное значение не заменять нулём; шаги и расчётные метры заменять вместе. Distance не используется. См. `v2-product-decisions.md`. Поступление реальных шагов и приоритеты телефон+браслет **не проверены** — P02/F02/Q01 остаются открытыми.

## 5. Следующая задача (предложение): объединённая V2.2b+V2.4b

**Обоснование объединения:** общая миграция, общий v2-репозиторий, общее решение о месте агрегата; V2.4b без долговечного `totalBookMeters` пользовательски готовой не объявляется.

- **Цель:** долговечный прогресс v2 и отдельный паспорт каждой экспедиции на базе схемы v3: четыре таблицы из раздела 1 с namespace `expeditionSeq`; `CreditStore` (маппинг строк одной экспедиции ↔ CreditLedger, sync-вход метров); `PassportStore` (маппинг, двухпроходный reconcile, атомарная транзакция по тому же `expeditionSeq`); восстановление после перезапуска. В первом релизе ровно одна активная v2-экспедиция, прежние строки сохраняются без UI истории.
- **Границы файлов (можно):** `ExpeditionDatabase.kt` (новые entity/DAO, MIGRATION_3_4 — строго аддитивно); новые `expedition/credit/CreditStore.kt`, `expedition/passport/PassportStore.kt`; unit + androidTest; фактические правки `v22b-proposal.md`/`v24b-passport-storage.md`.
- **Не трогать:** v1-путь целиком (`Expedition.kt`, v1-ветки repository/sync/ViewModel); слитые чистые модели `PassportV1`, `CreditLedger`/`DayCredit` (кроме согласованных интеграционных точек); `route/**`, `path/**`, `scene/**`, контракты `health/**`; навигацию и UI «Паспорт» (отдельная задача V2.4); пороги/тексты ROUTE.md; Gradle/подпись.
- **DoD:** восстановление CreditLedger и набора штампов **по одному `expeditionSeq`** после перезапуска (равенство снимков, включая NULL-даты); две экспедиции с одной датой не смешиваются; новая экспедиция начинает паспорт заново, прежние строки остаются; не более одной `ACTIVE`, переход при новом старте атомарен; двухпроходный reconcile; первое восстановление с прогрессом > 0 → все штампы NULL, baseline атомарно; скачок через исторический и новый пороги за один вызов (NULL + observedAt, идемпотентно); откат не отзывает штампы и не двигает baseline назад; null ≠ 0 и guards HC сохранены тестами; обновление поверх v1 без потери данных (цепочка v1→v4 на ручной старой схеме); v1 загружается, штампов не получает; существующие тесты зелёные без изменения ожиданий; **обязательный строгий review миграций, базовой линии и расчётов**; PR без автослияния.
- **Точка вызова reconcile: репозиторий v2 (CreditStore/PassportStore), не ViewModel** — транзакционность «дозапись + baseline» требует слоя БД; ViewModel читает готовый снимок.
