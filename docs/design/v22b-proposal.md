# V2.2b — предложение контрактов подключения CreditLedger (без кода)

Статус: предложение terra-research (2026-10-09), read-only аудит. Без кода, миграций и утверждения Distance или длины шага. Основание: `docs/design/V22A_CREDIT_TASK.md`, `docs/design/v22a-credit-calculation.md`, рамки `TODO.md` (k=20, без дневного лимита, D = 40 502 книжных км — единственная основа прогресса v2, старые экспедиции не пересчитываются). V2.2a слита в `main` (PR #16, `8e9e78e`; далее `36a3b6d`).

## Текущий путь данных

Health Connect `aggregate(COUNT_TOTAL)` без фильтра источника (`health/HealthConnectStepsGateway.kt:19-25`) → дневные окна в поясе экспедиции, первый день от `startedAt`, сегодня до `now`, окно скана 119 дней (`expedition/ExpeditionSync.kt:33-47`) → `null` = gap, день неизменён; явный 0 — подтверждённое значение (`:52`) → запись только после полного успешного скана; отзыв доступа посреди скана — ничего не пишется (`:64-67`) → заменяющая сверка `Expedition.reconcile` (Map.plus, stale-guard по `lastReadAt`, открытые записи при откате сохраняются, `Expedition.kt:55-60`) → Room v3 транзакционно (REPLACE для дневных, IGNORE для дневника, `ExpeditionDatabase.kt:104-144`) → UI читает только шаги v1.

Разрешения: только `READ_STEPS`. Стандартная граница чтения Health Connect — 30 дней **до момента первой выдачи** разрешения ([Read restrictions](https://developer.android.com/health-and-fitness/health-connect/aggregate-data)); после обычного перерыва данные с момента выдачи остаются доступны — граница меняется при отзыве разрешения или переустановке.

## Неизменные гарантии v1

1. Ветка v1 кода и схемы не меняется; `routeVersion == 1` продолжает шаговую модель; старые экспедиции не пересчитываются.
2. Ошибка/отзыв доступа не пишет нули; повторная сверка — замена, не инкремент.
3. Дни вне окна скана не очищаются; stale-guard по `lastReadAt`.
4. Молчаливой конверсии v1 → v2 нет: v2 начинается только явным новым стартом.

## Открытые вопросы владельцу (для постановки V2.2b)

1. Источник метров: Steps×stride vs HC `DistanceRecord` — не проверено на физическом телефоне (P02/F02); браслеты типа Zepp Life пишут только Steps, Distance может отсутствовать.
2. Длина шага: фиксируется на старте навсегда или пользователь может поправить; применяется ли смена к прошлым дням (SPEC запрещает молчаливый пересчёт).
3. История при длинном перерыве: реальный риск — окно пересканирования 119 дней в `ExpeditionSync` (корректировки старше него невозможны — подтвердить для v2). Стандартная граница HC (30 дней до первой выдачи разрешения) при перерыве данные не обрезает; смещается она при отзыве разрешения/переустановке — тогда часть ранних дней может стать недоступной. `READ_HEALTH_DATA_HISTORY` без доказанного сценария не предлагать.
4. Двойной учёт источников: официальный Aggregate API применяет приоритеты источников для Activity и удаляет дубли по пользовательским настройкам ([Aggregate data affected by user-selected apps priorities](https://developer.android.com/health-and-fitness/health-connect/aggregate-data)), поэтому `aggregate` без фильтра сам по себе дубли не суммирует; фактическое поведение телефон+браслет (приоритеты конкретных источников, браслеты типа Zepp Life пишут только Steps, Distance может отсутствовать) — проверить на реальном устройстве (P02/F02).
5. Пари на 80 дней «отдельно» для v2: как дедлайн сочетается с книжными метрами и целью D = 40 502 км.
6. Единица цикла освещения 30 км (влияет на то, что показывать из V2.2b: реальные vs книжные).
